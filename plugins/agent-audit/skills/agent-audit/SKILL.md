# agent-audit

An agent is a model using tools in a loop. When one fails in production, the model is rarely
the cause; usually a layer around it is missing: nothing caps the loop, every tool is granted,
nothing is remembered between runs, and "be careful" stands in for an approval step. This skill
checks an agent for each layer and writes down what is missing, with evidence from the file.

## Intake

Find the agent files before asking anything:

- Claude Code: `.claude/agents/*.md`, `~/.claude/agents/*.md`, and `agents/*.md` inside any
  folder that has `.claude-plugin/plugin.json` (a plugin agent).
- Other frameworks: the system prompt plus the code that sets tools, turn limits and approvals
  (`Agent(...)` in the OpenAI Agents SDK, a LangGraph graph, an n8n workflow).

Then ask in one message, only for what the files cannot tell you: what the agent is for, who
runs it, and which of its actions reach outside (send, publish, delete, spend). If the user
gives no answer, say what you assumed.

If a file says it is generated ("Generated by ...", "do not edit"), find the generator and its
sources now. Every fix goes there, never into the generated file.

## Workflow

1. **Lint.** For Claude Code agent files run:

       python scripts/check_agent.py <agent files or folders>

   It fails on what Claude Code would misread (an unknown or misspelled field is silently
   ignored, an invalid model, color, memory or maxTurns value) and warns on missing layers: no
   tool boundary, no `maxTurns`, no stop condition, no rule that read content is data, no
   approval rule, and fields a plugin agent ignores (`hooks`, `permissionMode`, `mcpServers`,
   `initialPrompt`). Fix every FAIL first. Other frameworks skip this step; apply the same
   questions by hand from `references/layers.md`.
2. **Judge the seven layers.** Work through `references/layers.md` for each agent. For every
   layer write PASS, GAP or RISK with a quote from the file or "absent". Judgment calls the
   script cannot make live here: is the description specific enough to win routing against its
   siblings, which tools are actually needed, and which actions are high-risk for this agent.
3. **Check the family.** With more than one agent, compare descriptions pairwise: two agents
   that claim the same request, and every `(use X)` handoff that names an agent or skill that
   does not exist. Also check each agent against installed skills that do the same job.
4. **Report.** One table per agent: layer, verdict, evidence, smallest fix. Order the findings
   by risk: approval and guardrails (L7, L6) first, then loop (L5), tools (L3), memory (L4),
   instructions (L2), model (L1). Close with what is shared across agents, since a fix in a
   shared template fixes them all.
5. **Fix on request.** Make the smallest edit that closes each gap, rerun the script, and show
   before and after counts. Rebuild a generated agent from its sources and run the repo's own
   staleness check.
6. **Write delegation tests.** For each agent, one realistic request that must route to it and
   one near miss from its "Not for" list that must not. If the repo has an eval format, write
   them in it; otherwise use the table in `references/layers.md`. Say that they were written,
   not run, until they are run.

## Rules

- **Evidence or nothing.** Every finding quotes the file or says the line is absent. No finding
  comes from the agent's name or from what such agents usually do.
- **An instruction is a wish; a permission is a guardrail.** Where a prompt rule could be a
  `tools` or `disallowedTools` entry, a hook, or a `permissions.deny` rule, say so. A plugin
  agent cannot carry hooks or a permission mode; name the project-agent or `hooks/hooks.json`
  route instead.
- **Do not cut tools you have not traced.** Before narrowing `tools`, list what each step
  actually calls (scripts it runs, files it writes, MCP servers it uses). A narrower list that
  breaks a step is worse than a warning.
- **Do not change the model without evals.** Recommend a smaller model only for a step with a
  passing eval set on that model.
- **Never run the agent against production** to test it, and never send, publish, delete or
  spend while auditing.

## Output

```
<agent>: <n> RISK, <n> GAP, <n> PASS
| Layer | Verdict | Evidence | Fix |
...
Shared across agents: <one line per template-level fix>
Tests written: <n> (not run) | run: <pass>/<total>
```
